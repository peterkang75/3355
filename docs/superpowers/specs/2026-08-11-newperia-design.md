# 신페리오(New Peria) 경기방식 추가 — 설계

작성일: 2026-08-11

---

## 1. 배경

경기방식에 신페리오를 추가하고 싶다는 요청. 검토 과정에서 두 가지가 드러났다.

**신페리오는 경기방식이 아니라 핸디캡 산출 방식이다.** 스트로크로 치되 핸디캡을 그날 스코어에서 뽑는다. 다만 운영 단순성을 위해 경기방식 목록에 나란히 넣기로 확정했다(엠브로스+신페리오 같은 조합은 지원하지 않음).

**3355는 신페리오가 푸는 문제를 이미 풀어놨다.** 활성 정회원 25명 중 24명(96%)이 핸디캡 등록 완료, 그레이드 A~D 운영 중, 당일 핸디캡 지정 기능도 있음. 따라서 메인 방식 교체가 아니라 **선택지 추가**로 접근한다.

**남는 실익:** 게스트(핸디캡 등록 0명 — 7월 라운딩에 6명 참가), 등록 핸디캡의 노후화, 이벤트성 변화.

---

## 2. 신페리오 계산식

```
핸디캡 = (지정 12홀 합계 × 1.5 − 코스파(72)) × 적용률
넷     = 18홀 그로스 − 핸디캡
```

지정 12홀의 점수는 핸디캡 산출과 18홀 그로스에 **모두** 반영된다(신페리오의 원리, 정상).

---

## 3. 적용률 — 시뮬레이션 근거

**전제:** 24명, 평균 그로스 82(10오버) ~ 107(35오버) 균등 분포, 파72, 12홀 무작위 추첨, 8만 회 시행. 홀당 편차는 실력에 비례(검증: 목표 82/94/107 → 실측 82.1/94.1/107.2, 홀당 편차 1.04/1.39/1.76타).

실력순 6명씩 4구간 우승률 (완전 공정 = 각 25.0%):

| 적용률 | 최상위6 | 중상위6 | 중하위6 | 최하위6 |
|---|---|---|---|---|
| 80% | 41.4% | 25.7% | 18.7% | 14.2% |
| 85% | 30.2% | 25.8% | 22.8% | 21.2% |
| 88% | 25.2% | 24.8% | 24.7% | 25.3% |
| 90% | 22.3% | 24.0% | 25.7% | 28.0% |

**핵심:** 잔여 실력 우위 = (1 − 적용률) × 실력편차. 3355는 편차 25타라 80%면 5타가 그대로 남아 상위권이 약 3배 유리하다. 표준 80%는 편차가 좁은 모임 기준.

**완전 균형점은 88%** (기복 모델에 따라 85~91%). 다만 88%는 사실상 추첨이라 잘 친 사람이 보상받지 못한다. **기본값 85%** — 상위권 1.4배 우위로 실력이 약간 반영되면서 최하위 그룹도 21% 확률.

적용률은 **라운딩별로 입력 가능**하게 한다(기본값 85%).

## 4. 확정 사항

| # | 항목 | 결정 |
|---|---|---|
| 1 | 배치 | 경기방식 목록에 추가 (스트로크·포썸·엠브로스와 나란히) |
| 2 | 적용률 | 라운딩별 입력, 기본값 85% |
| 3 | 핸디캡 소수점 | **유지** (14.4 그대로). 앱 전체 소수점 허용 선행 |
| 4 | 핸디캡 상한 | 없음 |
| 5 | 그레이드 | 신페리오 라운딩에서는 사용 안 함 (설정 UI 숨김) |
| 6 | 시상 | 전체 1·2·3등 |
| 7 | 12홀 지정 | 경기 전후 언제나 가능 + 지정자·시각 기록 + 변경 시 경고 |
| 8 | 우승자 맞추기 | 신페리오 라운딩에서는 비활성화 |

**그레이드를 끄는 이유:** 그레이드는 실력대를 갈라 각 대에서 우승자를 뽑는 공정성 장치다. 신페리오가 전체 판에서 이미 공정성을 달성하므로, 그 위에 그레이드를 얹으면 소규모 추첨을 4번 하는 것에 불과하다. 조편성에는 그레이드를 쓰지 않으므로(코드 확인) 꺼도 조 편성에 지장 없다.

**12홀 자유 지정의 위험과 대응:**
- 스코어 확인 후 지정 가능 → 조작 의혹. 지정자·시각 기록으로 제비뽑기 시각과 대조 가능하게 함
- 재지정 시 우승자 소급 변경 → 변경 경고창
- 지정 전 순위 부재 → 그로스 순위 + 안내 문구 표시

## 5. 선행 작업 — 핸디캡 소수점 허용

신페리오 핸디캡은 소수점 첫째 자리까지 나온다(예: 14.4). 현재 앱은 여러 곳에서 핸디캡을 정수로 깎고 있어 이대로면 신페리오가 무의미해진다. **신페리오와 별개로 기존 스트로크 라운딩의 순위 정확도도 개선되므로 먼저 처리한다.**

### 고칠 곳 — 계산부 반올림 제거 (4)

| 파일 | 위치 | 증상 |
|---|---|---|
| `src/utils/roundingRanking.js` | 73 | `Math.round` → 라운딩 결과·우승자 순위가 정수 핸디로 계산 |
| `src/pages/Leaderboard.jsx` | 200 | 동일 |
| `src/pages/PickWinner.jsx` | 160 | **그레이드 분류**를 반올림 핸디로 판정 → 리더보드(소수점 그대로)와 불일치. 핸디 18.4가 여기선 B, 리더보드에선 C로 갈릴 수 있음 |

> **조사 후 정정:** 초안에 넣었던 `src/pages/Play.jsx:2204`는 **고치지 않는다.** 그 값은 `allocateStrokes()`(스테이블포드 홀별 스트로크 배분)에만 쓰이며 정수여야 한다. `stableford.js:34`와 같은 사유.

네트 스코어가 소수로 바뀌므로 **표시부는 소수점 1자리로 포맷**한다.

### 고칠 곳 — 입력창 소수점 허용 (2)

| 파일 | 위치 | 증상 |
|---|---|---|
| `src/pages/MemberDetail.jsx` | 529, 536 | `inputMode="numeric"` → 모바일 키패드에 소수점 없음 |
| `src/pages/MyPage.jsx` | 449, 461 | `type="number"` (GA Handy·House Handy 둘 다) |
| `src/pages/MemberInfoForm.jsx` | 358, 375 | `inputMode="numeric"` (GA·House 핸디캡) |
| `src/pages/Admin.jsx` | 2282 | `inputMode="numeric"` (회원 정보 수정) |
| `src/pages/booking/CreateBookingModal.jsx` | 410 | `type="number"` 단독 (게스트 핸디캡) |

이미 소수점을 받고 있어 손대지 않은 곳: `JoinPage`, `GuestJoin`, `ParticipantManagement`(step=0.1), `HostManageSheet`, `Admin:2573`.

공통 헬퍼 `round1()`을 `src/utils/index.js`에 추가해 4곳이 아닌 한 곳에서 관리한다 — 단순 뺄셈은 `60 − 32.2 = 27.799999999999997` 같은 부동소수점 잔재가 화면에 노출된다.

**기준 패턴은 `src/pages/JoinPage.jsx:421,430`** — `type="text" inputMode="decimal"` + `replace(/[^0-9.]/g,'')` + placeholder "예: 18.4". 이 방식을 그대로 적용한다.

### 고치지 않는 곳

`src/pages/Play.jsx:2204`, `src/utils/stableford.js:34` — `Math.round(hcp)`. 스테이블포드는 핸디캡을 홀별 스트로크로 배분하므로 정수여야 한다. 0.4타는 배분 불가. **정상 동작이므로 유지.**

### 영향 없음 확인

- DB 스키마: `handicap`/`gaHandy`/`houseHandy` 모두 `String?` → 소수점 저장 가능
- 서버: `parseFloat` 사용 중 → 소수점 처리 가능

## 6. 신페리오 구현 설계

### 선행 — gradeSettings 덮어쓰기 버그 (Step 0, ✅ 2026-08-11)

`gradeSettings` 한 필드에 `mode`(경기방식)와 `gradeA~D`(그레이드)가 함께 들어가는데, 저장 경로 두 곳이 **통째로 덮어써서** 서로를 지우고 있었다.

- `RoundingManagement.jsx:119` → `PUT /bookings/:id` → `{mode}`만 저장 → **그레이드 소멸**
- `GradeSettings.jsx:54` → `PATCH /bookings/:id/grade-settings` → `{gradeA~D}`만 저장 → **mode 소멸** (`roundingRanking.js:13`이 `mode || 'stroke'`라 조용히 스트로크로 되돌아감)

**실측 피해:** 전체 라운딩 53건 중 mode와 그레이드가 **둘 다 살아있는 건 0건**. 6건(1·2·3·5·6월 정기라운딩, 연말 총정기모임)은 mode가 유실됨. 원래 값의 기록이 없어 복원 불가 — 손대지 않음.

**신페리오에 치명적:** 적용률·12홀 지정을 이 필드에 저장하므로, 고치지 않으면 라운딩 정보를 한 번만 수정해도 제비뽑기 결과가 날아간다(재현 불가).

**조치:** `server/utils/gradeSettings.js`에 `mergeGradeSettings()` 단일 소스 신설. 두 라우트 모두 기존 값을 읽어 병합 후 저장. 서버에서 막으므로 앞으로 추가되는 호출부도 자동 안전. 키 삭제는 `null`을 명시적으로 보낸다(키 생략 시 기존 값 유지). 단위 테스트 12건 통과.

### 저장 위치

`Booking.gradeSettings` JSON을 확장한다. 현재도 이 필드에 `mode`(경기방식)를 저장하고 있어 일관되며, **DB 스키마 변경이 불필요**해 배포 위험이 없다.

```json
{
  "mode": "newperia",
  "newPeriaRate": 0.85,
  "newPeriaHoles": [1,3,4,6,7,9,10,12,13,15,16,18],
  "newPeriaSetBy": "<memberId>",
  "newPeriaSetAt": "2026-08-11T20:15:00.000Z"
}
```

`newPeriaHoles`가 없거나 길이가 12가 아니면 "미지정" 상태로 간주한다.

### 화면

> **구현 중 정정 (2026-08-11):** 초안은 `BookingForm`·`RoundingManagement`에 UI를 배치했으나 **두 화면 모두 앱에서 도달 불가**였다. `App.jsx`가 `Booking.jsx`를 import하지 않고(→ `BookingForm` 사용처 없음), `/rounding-management`로 이동하는 링크도 없다. 실제 경로는 `RoundingListV2` → `HostManageSheet`(바텀시트) 하나뿐이다.
> **교훈:** 파일명이 아니라 `App.jsx` 라우트 + 실제 navigate 호출로 도달 가능성을 먼저 확인할 것.

**경기방식 선택 (HostManageSheet → 고급 설정 → 게임 방식)**
`신페리오` 버튼 추가. 선택 시 안내 문구 노출. 그레이드 설정 진입은 숨김.

**12홀 지정 + 적용률 (HostManageSheet 기본 화면 → "신페리오 홀 지정하기")**
'조편성 하기' 아래 버튼. 1~18 격자에서 12개 선택 + **적용률 입력을 같은 시트에** 배치(사장님 요청 — 순위가 나오기 직전이 조정하기 자연스러운 시점). 12개 미만이면 저장 불가. 저장 시 지정자·시각 자동 기록. 기존 지정이 있으면 변경 경고창. 지정 취소 시 적용률은 보존.

**리더보드 / 라운딩 결과**
- 미지정: 그로스 순위 + "신페리오 홀 지정 전입니다" 안내
- 지정 완료: 신페리오 넷 순위. 행마다 그로스·핸디(소수점 1자리)·넷 표시. 하단에 지정 이력 표시
- 시상: 전체 1·2·3등

**우승자 맞추기 (PickWinner)**
`mode === 'newperia'`인 라운딩은 목록에서 제외.

### 계산 위치

`roundingRanking.js`와 `Leaderboard.jsx` **양쪽에 각각** 신페리오 분기를 넣는다.

> **초안 정정:** "두 곳을 공용 함수로 통합"이라고 썼으나 조사 결과 `Leaderboard.jsx`는 `roundingRanking.js`의 상위집합이다 — 포썸 팀 넷(283~343), 2BB 베스트볼(526), 팀 순위 표시(844, 1001)가 리더보드에만 있어 드롭인 교체가 불가능하다. 통합하면 스트로크·포썸·엠브로스·2BB·스테이블포드 전 모드 회귀 검증이 이번 기능에 딸려온다. **통합은 별도 과제로 분리**(plan.md 기존 항목 "리더보드 순위계산 공용함수 통합"에 유지).
